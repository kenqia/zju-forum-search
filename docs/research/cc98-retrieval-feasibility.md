# CC98 查询时检索可行性研究结论

## 范围

本文沉淀截至 2026-09-15 已完成的资料阅读、原型实现和用户环境实测，不包含新的网络调查。原始查询、候选标题、链接和人工标签只留在用户本机，不写入仓库。

详细实验过程见[查询时检索可行性实验](../experiments/query-time-retrieval-feasibility.md)。产品词汇和使用边界见[领域上下文](../../CONTEXT.md)。本文只记录能指导下一步实现的结论。

## 结论

CC98 的查询时检索路线值得继续。校园网直连环境已经验证以下链路：扩展读取页面现有短期 access token，调用主题搜索接口，顺序执行多个检索词，合并去重候选，并在页面内展示和标记结果。

这不等于自然语言搜索已经通过验收。现有实测只证明关键词检索、候选合并和受控请求可用。第三方模型生成的查询计划与 CC98 召回尚未完成联合测试，30 条盲测也未运行。因此，当前准确表述是“核心检索机制可行，通用自然语言效果待测”。

WebVPN 页面能够加载扩展，但零额外权限方案无法稳定取得 CC98 登录态。首版只承诺校园网直连。WebVPN 不应再靠猜测存储位置继续试探。

## 一手资料确认的事实

### 搜索接口

- CC98 官方桌面前端使用 `GET /topic/search`，参数包括 `keyword`、`from` 和 `size`。[官方桌面前端源码](https://github.com/ZJU-CC98/Forum/blob/a53c5cf1f89793d26aa17ef168a5256a8bb59c34/Utility.tsx)
- CC98-V4 客户端还定义了板块内搜索路径 `/topic/search/board/{boardId}`。[CC98-V4 搜索服务源码](https://github.com/ZJU-CC98/CC98-V4/blob/7ccb83f3ba085e8e03749423264325b4cea1756d/src/service/topic.ts)
- 官方客户端实现提供了可供前端调用的关键词搜索，但没有公开服务端匹配字段、分词方法或频率阈值。不能从客户端代码推导服务端必然执行 AND、OR、标题匹配或正文匹配。

### 认证

- CC98 官方桌面前端把 access token 及到期时间保存在浏览器存储中，值带有前端自己的序列化前缀。[官方存储实现](https://github.com/ZJU-CC98/Forum/blob/a53c5cf1f89793d26aa17ef168a5256a8bb59c34/Utility/storageUtility.ts)
- 该事实只说明官方前端的直接访问实现。它不能证明 WebVPN 改写页面后，扩展隔离环境仍能看到同一份存储。

### WebVPN URL

- CC98-CLI 提供了 WebVPN URL 转换代码，可作为路径构造参考。该项目使用 MIT License，但它不是浙江大学 WebVPN 的接口承诺。[CC98-CLI WebVPN 实现](https://github.com/Lucent-Snow/CC98-CLI/blob/38b54a4f49d5c77bc5d7fad779829cf1a041ca65/src/api/webvpn.ts)

### 模型接口

- 阿里云 Model Studio 文档列出了 `qwen3.8-27b` 及其调用方式。[模型说明](https://www.alibabacloud.com/help/en/model-studio/qwen3-8-27b)
- Model Studio 提供结构化输出能力，适合让查询规划器返回可校验的 JSON，而不是自由文本。[结构化输出文档](https://www.alibabacloud.com/help/en/model-studio/qwen-structured-output)

## 用户环境实测

以下结果来自用户本人已授权的 Edge 和 CC98 会话。它们是环境观测，不是 CC98 官方保证。

| 项目 | 结果 | 能证明什么 |
| --- | --- | --- |
| 校园网直连认证 | `/me` 成功 | 扩展能临时使用直接页面的短期 token |
| 单个高信号关键词 | 1 次请求，约 0.1 秒，20 个候选 | 搜索请求、解析和卡片展示可用 |
| 两个空格分隔的高信号词 | 1 次请求，约 0.1 秒，12 个候选 | 多词输入能在该样本中收窄候选 |
| 加入更精确约束 | 1 次请求，约 0.1 秒，1 个相关候选 | 精确组合有较强收窄作用，也有漏召回风险 |
| 5 个手工检索词，3 秒间隔 | 5 次请求，13.4 秒，19 个去重候选 | 顺序请求、合并去重和重复命中统计可用 |
| 同组检索词，2 秒间隔 | 5 次请求，8.4 秒，19 个去重候选 | 2 秒间隔在该次实验中未触发限制 |
| 约 450 毫秒间隔 | 第 2 次请求收到 HTTP 403 | 该节奏不可用，不能据此确定精确阈值 |
| WebVPN 页面注入 | 扩展入口可显示 | URL 匹配和内容脚本注入可行 |
| WebVPN 登录态复用 | 多轮零权限桥接仍无法取得 token | WebVPN 认证路径尚不可用 |
| Qwen 规划服务 | 合成输入得到合法结构化计划，HTTP 200 | 本地 FastAPI 到模型的规划链路可用 |

完整的匿名运行记录和验收门槛见[实验文档](../experiments/query-time-retrieval-feasibility.md)。

## 从证据得到的推断

这些判断有实测支持，但不是平台公开语义。

1. 空格分隔的高信号词在已测样本中明显收窄结果。模型应同时生成精确组合、稳定简称和较宽的补充检索词，而不是只发一条长自然语言。
2. 精确词组容易提高精度，也可能漏掉使用简称或不同学期表达的帖子。多检索词合并是必要的召回补偿。
3. 450 毫秒触发 403，而 2 秒完成 5 次请求。现阶段可把 2 秒当实验值，但不能称为平台限流规则。任何 403 或 429 都应终止本轮，不自动重试。
4. 多次命中是有用信号，但不能单独决定排序。实测中，高价值候选不一定都靠重复命中进入前五。
5. WebVPN 失败可能来自页面改写、存储隔离或认证生命周期。现有证据不能确定具体根因。继续扩大探测范围会增加权限和凭据风险，收益不明。

## 已决定的路线

### 查询时检索

首版不建立 CC98 全站索引。每次查询使用用户自己的授权即时获取候选，避免保存全站副本。召回上限因此受 CC98 搜索接口限制，也不能承诺穷尽历史内容。决策依据见 [ADR-0001](../adr/0001-query-time-retrieval.md)。

当前实验不使用回帖发现主题，也不在搜索阶段批量读取回帖。必要时只为前五条读取主楼。ADR-0001 中“读取文字回帖参与重排”的旧描述已被当前[领域上下文](../../CONTEXT.md)和[实验范围](../experiments/query-time-retrieval-feasibility.md)取代，后续应单独修正文档。

### 查询规划与本地排序

浏览器内的通用分词会拆开领域短语，并生成低价值组合。它保留为失败对照，不再增加课程名、年级或求职词表等硬编码规则。

当前方案让 `qwen3.8-27b` 只接收用户查询并返回结构化查询计划，内容包括检索词、必须概念、排除词和时间约束。论坛候选、正文、回帖、认证数据和个人背景不进入模型请求。浏览器本地完成候选合并与重排。具体数据边界和回滚方式见 [ADR-0003](../adr/0003-third-party-query-planning.md)。

当前形态不再保留本地 FastAPI 和可行性原型：模型密钥保存在 `chrome.storage.local`，service worker 直连用户配置的 OpenAI 兼容端点。技术栈选择见 [ADR-0002](../adr/0002-mvp-technology-stack.md)，迭代规划与数据边界见 [ADR-0003](../adr/0003-third-party-query-planning.md) 和 [ADR-0004](../adr/0004-iterative-search-with-title-feedback.md)。`backend/` 与 `frontend/prototypes/` 已删除。

### 请求纪律

- 快速搜索使用 20 秒预算，深度搜索使用 60 秒预算。
- 请求顺序执行，当前实验间隔为 2 秒。
- 每个检索词先取一页，每页 20 条。剩余时间允许时再分页。
- 收到 401、403、429、登录跳转或超时后立即停止，并保留已经取得的候选。
- 2 秒只是在一次 5 请求实验中成功。出现限制响应时恢复到已验证的 3 秒，不继续压缩。

### WebVPN

扩展首版清单只匹配校园网直连页面。WebVPN 页面注入可行，但登录态复用未通过，相关桥接代码不再加载。若恢复这条路线，需要先评审新增脚本执行权限或独立认证流程的安全影响，再做单独原型。不能把“WebVPN 页面能打开 CC98”当成“扩展能授权调用 CC98 API”。

## 尚未证明

- CC98 搜索具体匹配标题、主楼、回帖还是其他字段。
- 空格分隔关键词的确切布尔语义。
- 403 的判定条件、时间窗口和精确请求阈值。
- 模型规划能否在 15 条开发查询上达到 Top-5 成功率 80%。
- 深度搜索能否达到相对人工候选池 70% 的召回率。
- 30 条盲测是否达到相同门槛。
- 本地重排能否稳定把最有用候选排进前五。
- WebVPN 下如何在可接受的权限边界内复用登录态。
- 当前路线对回帖中独有信息的漏召回程度。

## 下一步验证

下一轮只做校园网直连下的联合验收。对同一批开发查询分别运行原句基线和 Qwen 查询规划，合并候选池后人工标注，再独立计算候选召回和 Top-5 排序效果。通过开发集后再运行盲测。

如果所有查询规划器都无法达到 70% 的候选池召回率，应缩小产品承诺，或在取得 CC98 管理方许可后再研究本地索引。不要用界面优化掩盖候选缺失。
